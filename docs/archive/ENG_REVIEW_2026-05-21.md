### 1.4. [P1] (confidence: 9/10) Realtime 히트맵 아키텍처 미정

PRD §5.4: "Supabase Realtime으로 다른 멤버의 가능 시간 합산 표시" + §15.1 "60fps 유지". **하지만 broadcast 모델이 명시 X.**

방안:
- (A) **Postgres LISTEN/NOTIFY로 votes table 변경 시 broadcast.** 모든 클라이언트가 receive → 클라가 로컬 합산. 5명 모임에 평균 200 cell 투표 → 1000 broadcast events × N members.
- (B) **Realtime broadcast channel + Edge Function에서 합산 후 push.** 서버가 heatmap aggregate 계산 → broadcast. 모든 클라가 합산된 결과만 receive.
- (C) **Database trigger → materialized view → Realtime postgres_changes on view.** PG 11+ continuous aggregates.

**권고: B + 100ms 클라이언트 debounce.** 이유: 60fps 유지하려면 클라에서 합산 X. 1000+ events × 7명 모임 = 7000 events/s 처리 불가. Edge Function이 votes 변경 received → 같은 모임의 votes를 group_id로 fetch → heatmap aggregate (slot별 카운트) → broadcast. 클라는 receive → setState. 100ms debounce로 burst 처리.

연결: 잘-tested > 빨리-tested. Phase 1+2이 시간 그리드 + 히트맵에 회사의 운명을 걸기 때문에 이 부분이 60fps 안 나오면 전체 가치 제안이 무너짐.

### 1.5. [P1] (confidence: 8/10) Coordinate system 통일

PRD §5.7: 네이버 지도 + 카카오 Local API. 네이버는 WGS84 (lat/lng). 카카오 Local API는 default WGS84지만 `WTM`, `TM`, `KTM`, `BESSEL`, `WCONGNAMUL` 모두 지원. **호출 시 명시 안 하면 마커가 km 단위로 어긋난다.**

**권고:** 모든 카카오 Local API 호출에 `?x={lng}&y={lat}` (WGS84) 명시 + 응답 좌표도 WGS84 명시 확인 + 어디 한 군데 normalization layer (`coords/normalize.ts`) 만들고 모든 외부 좌표가 이 layer 통과하게.

### 1.6. [P1] (confidence: 7/10) Branch.io PoC를 Phase 1+2 build에 앞서

### 1.7. [P1] (confidence: 9/10) Calendar sync 권한·취소 흐름

- Push 부분 실패 시 호스트에게 "일부 멤버 캘린더 추가 실패" 알림 + 멤버 list.

## §4. Performance Review

### 4.1. [P0] (confidence: 9/10) 시간 그리드 60fps target — 구현 spec

PRD §15.1: "60슬롯 × 7일 = 420셀 드래그 60fps". **순진 구현은 매 cell touch에 setState → 전체 grid re-render → 16ms budget 초과.**

**권고 구현 spec:**
1. Drag gesture는 **`react-native-gesture-handler` + `react-native-reanimated` worklet** (UI thread). JS thread 영향 0.
2. Cell 상태는 **`useSharedValue` (Reanimated)** — JS state 안 거치고 native에서 색 변경.
3. Vote commit (서버 sync)은 **drag 종료 시 1회** + 100ms debounce — 중간 update broadcast 안 함.
4. Heatmap rendering은 **`FlashList` 또는 `RecyclerListView`** (60slot × 7day가 720 cell DOM이 되면 felt jank — 가상화 필수). Or simple 2D grid with React.memo on each cell.
5. Heatmap update receive는 **별도 Reanimated shared value** (JS state X) — broadcast받으면 native shared value 업데이트.

**측정 기준:**
- Profiler로 frame drop 측정 (Hermes profile 또는 Flipper Performance).
- 7명 모임 × 동시 투표 부하 테스트 (load test script + Realtime simulation).
- 저사양 디바이스 baseline: iPhone SE 2nd gen + Galaxy A14 (베타 페르소나 P1 학생 기기).

### 4.2. [P1] (confidence: 8/10) Kakao Local API quota·cost 명시

PRD §11.2 + §7.1: 카카오 Local API single source for 매장 검색. **Free tier 한도·유료 가격 명시 X.**

**권고:**
- Build 시작 전 Kakao 디벨로퍼스 quota check (현재 일 30만 호출 무료, 그 이상 유료).
- Viewport 이동 debounce (300-500ms) + 5분 viewport 격자 캐싱은 client side. Server-side proxy 도입하면 추가 quota 절약 + per-user limit 적용 가능.
- **Quota 한도 도달 시 fallback UX 명시** — "잠시 후 다시 시도" 또는 캐시된 결과만 표시.
- **베타 1000 DAU × 평균 10회 viewport 이동 = 10000 호출/일 → 한도 안.** 그러나 가능한 viral 시점에 burst 발생 가능.

### 4.3. [P1] (confidence: 7/10) Cold start 최적화

PRD §11에 listed RN libraries 다수 → Expo 콜드 스타트 무거움.

**Phase 1+2 cold-start critical libraries (always load):**
- expo-router, react-native, supabase-js, zustand, expo-secure-store

**Lazy-loadable (route 진입 시):**
- `@mj-studio/react-native-naver-map` — 지도 탭 진입 시
- `expo-calendar` — 모임 확정 + Calendar push 시점
- Branch SDK — 첫 진입 attribution check 시 (그러나 SDK init은 startup)
- Gemini Vision (제외 시 N/A)
- 토스 webview (Phase 1+2은 안 씀, Phase 3에 옮김)

**측정:** EAS Build production binary 콜드 스타트 측정 (iOS·Android × 저사양·중사양 4조합). Target: < 2초.

### 4.4. [P2] (confidence: 7/10) Calendar push fan-out rate limiting

Host가 시간 확정 → 멤버 10명 Google Calendar + 5명 Apple Calendar push.

**문제:** Supabase Edge Function 1회 호출이 외부 API 15개 호출 trigger. Google Calendar API per-user quota = 1M/day, but per-second QPS는 더 빡빡. Edge Function timeout (60s default).

**권고:**
- Push fan-out을 background queue (Supabase Function Hook + `pg_cron`)로 분리. 호스트 액션은 즉시 응답, push는 비동기.
- Per-user QPS limit 미리 측정.
- 실패 시 retry (max 3) + 호스트에게 partial fail report.

- **Step 14 (OCR) ↔ Step 5 (Calendar sync)** — OCR이 schedules에 매주 반복 일정 INSERT, Calendar sync가 같은 schedules table 사용. `source = 'everytime'` enum 격리로 충돌 없음. 다만 OCR 일정의 캘린더 push 여부 결정 필요 — **권고: OCR 일정은 외부 push 안 함** (사용자 외부 캘린더 폭격 회피, 학기 시간표는 앱 내 표시 only).
- **Step 15 (지도-일정 mode) ↔ Step 6 (지도)** — 같은 네이버 지도 컴포넌트, 다른 mode prop. `<MapView mode="search" | "schedule">` 분기. mode 전환 시 마커 set 교체 + 폴리라인 toggle.
