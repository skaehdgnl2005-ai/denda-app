## §1. Problem Statement

한국 친구 모임 (대학생 팀플, 직장인 회식·동호회·데이트)에서 시간 맞추기 + 장소 결정 + 예약이 분산된 도구로 처리되어 평균 30시간+ coordination burn 발생.

**Raw data anchor (N=1):** 정의진, 2026-05-03, 5명 팀플 단톡:
- 카톡 투표로 날짜 정함 (날짜는 작동)
- 시간 맞추기 fail (30시간 burn)
- 결국 3명만 참석 (40% drop rate)
- 카페·스터디룸 추정 use case

## §2. Demand Evidence

| 항목 | 강도 | 상세 |
|---|---|---|
| Prior MVP scale | 약 | 30명 지인 base, 시간 맞추기 only 웹, 1년+ 운영 |
| 외부 fresh case | 강 (N=1) | 정의진 case (30시간 burn, 40% drop) |
| 식당 supply | 중 | 안암 20곳 사인 (음식점·술집, **카페 0곳**) |

**Critical observation:** Demand evidence는 P1 (대학생 카페·도서관) 한 명, Supply evidence는 P2 (직장인 음식점·술집) 20곳. 두 user pool 정렬 미검증. PRD §2.3의 "카페 제외 = 객단가 논리"는 post-hoc 합리화 — 실제 이유는 "카페는 예약 시스템 자체가 없어서 제휴 불가" (founder 직접 확인). Supply constraint가 BM 선택을 결정.

## §3. Status Quo (시간 맞추기 pain)

- **가장 흔함**: 카톡 단톡 메시지 폭격 → 정함 or 못 정함. 평균 80-150 메시지, 3-5일.
- **카톡 투표 기능**: 날짜 정하기에는 부분 작동, 시간 정밀도 0
- **When2meet / Doodle**: 한국 일부 segment, 회원가입·영어 UX 마찰
- **호스트 일방 결정**: 안 맞는 사람 빠짐 (40% drop, 정의진 case 검증)

## §4. Target User & Wedge

**Anchor: 정의진 (5명 팀플 단톡, 5/3, 30시간 burn).** Demand evidence의 sole external data point.

**근데 정의진은 supply 안 맞는 카테고리 (카페·스터디룸).** 진짜 BM customer는 P2 (직장인 회식·동호회·데이트, 음식점·술집). P2 raw data = 0.

**채택 wedge: β-compact의 Phase 1+2** — 시간 그리드 + 모임 + 캘린더 동기화 + 지도 + "예약하기" click-through 측정. 실제 결제 없음. 4-6주 burn 대신 ~3-4주.

## §5. Constraints

- 안암 지역 한정 베타 (운영팀 1:1 카톡 채널 SLA 48h)
- 한국어 only (베타)
- 카카오 비즈앱 우회 OAuth (synthetic email + HMAC)
- 식당 20곳 retention 시계 12주+ → 명시적 communication 패키지 필요
- Prior MVP 30명 user는 새 앱으로 안내 (데이터 미이전, 카톡 환영 메시지)

## §7. Cross-Model Perspective (Claude subagent cold read)

> **Strongest 버전:** "친구 5명이 점심 한 끼 정하는 데 30시간 burn하는 걸 30초로 줄이는 single-tap coordination layer. 카톡 위에 얹히는 decision engine. 캐치테이블이 식당 검색 layer라면 된다는 group decision layer고, 이건 카톡이 절대 안 만들 product. Ceiling은 한국 모든 친구·동호회·팀플 모임이 default로 통과하는 coordination protocol."

> **Reframe 가설:** Product의 핵심은 "coordination failure 방지", 결제는 monetization 수단. PRD 1014줄 중 70%가 BM·정산·법무 — 정의진은 그 중 하나도 필요로 한 적 없음. "잃은 건 30시간과 친구 2명이지 돈이 아님."

> **Falsifiable prediction:** "Gate #2 click-through < 10% 나옴" — coordination이 standalone product고 reservation이 optional add-on이라는 가설.

> **추천 prototype:** Next.js + Supabase + Solapi 카톡 알림톡, 결제·식당·노쇼·환불 전부 skip. 1주.

**Founder decision:** Cold read reframe을 β-compact의 gate interpretation layer로 박음 (전체 채택은 X). Gate #2 < 10% 시 즉시 reframe 결정 (3-path: coordination-only / 식당 timeline 재조정 / P2 segment 별도 acquisition).

## §8. Approaches Considered

### α: Minimal wedge (카톡 게스트 페이지 only)
- Effort: S (1-2주) / Risk: Low / BM: 0
- 거부 이유: BM 부정, 20곳 sunk cost 휘발, founder의 strategic intent 부정

### β: Phased PRD (3단계 독립 launch)
- Effort: L (PRD 동일 분산) / Risk: Med / BM: Phase 3부터
- 거부 이유: Phase 1·2 분리 출시가 모바일 ramp 시계 늦음

### γ: Current PRD all-in
- Effort: XL (4-6주 burn before launch) / Risk: High / BM: 즉시
- 거부 이유: 5개 premise 동시 베팅, P3·P5 검증 0인 채로 토스·변호사·통신판매업 burn

### β-compact (채택)
- Phase 1+2 묶음 모바일 출시, 새 codebase + 새 Supabase project
- Phase 3 = Gate decomposition 통과 후만 commit
- + Cold read interpretation layer
- + 식당 retention 패키지

## §9. Recommended Approach — β-compact 상세

### §9.1. Phase 1+2 Scope (모바일 첫 출시, ~3-4주)

**클라이언트:**
- RN/Expo SDK 53+
- 카카오 OAuth (비즈앱 우회: synthetic email + HMAC)
- 시간 그리드 + 실시간 히트맵 (Supabase Realtime, 15분 단위)
- 캘린더 동기화 (Google Calendar + Apple iOS via expo-calendar)
- 네이버 지도 SDK (`@mj-studio/react-native-naver-map`) + 카카오 Local API
- 카테고리 필터 + 반경 조절 + 동적 매장 검색 + 제휴 마커 강조
- "예약하기" 버튼 click-through 측정만 (실제 결제 X, 토스 가맹 X)
- 식당 20곳 정보 display only (no booking flow, partnerships table read-only)
- 푸시 알림 F1-F5 (소셜 + 모임). F6·F7 (예약) = Phase 3
- 다크모드 (시스템 자동)
- 약관·개인정보 동의 모달

**백엔드:**
- 새 Supabase project (prior MVP 별도 운영)
- 새 schema 설계 (partnerships/reservations/payments/payouts 도메인 깨끗하게 분리)
- Edge Functions for 푸시 알림 트리거
- 30명 prior MVP user는 새 앱 transition (카톡 환영 메시지 + 닉네임 기억)

**비포함 (Phase 3):**
- 토스페이먼츠 결제 위젯
- 통신판매업 신고
- 변호사 약관 검토
- 식당 활성화 (사인 → 첫 결제 trigger)
- 실제 예약·정산·환불·노쇼 flow
- 푸시 F6·F7 (예약)

### §9.2. Decomposed Gate (PRD §13.2 update)

```
Phase 2 launch (W0)
  ↓
W0-W2: baseline 수집 (gate 적용 X)
  ↓
W2: 자체 data로 gate threshold final calibrate
  ↓
W2-W8: gate monitoring
  ↓
Gate #1 (모임 확정 → 장소 확정 비율):
  ≥ 40% → 강한 신호
  20-39% → 보류 (UX 개선 + 2주 추가 측정)
  < 20% → 장소 기능 가설 무너짐

Gate #2 (장소 확정 → "예약하기" click-through):
  ≥ 25% → 강한 신호
  10-24% → 보류 (P1 학생 vs P2 직장인 segment 분리 측정)
  < 10% → cold read framing 검증 — coordination-only reframe 결정

Combined:
  Gate #1·#2 모두 강한 → Phase 3 full commit
  하나만 강한 → 약한 단계 진단 + 부분 commit
  둘 다 보류 → Phase 2 연장 + segment 분리
  Gate #2 < 10% → 3-path 결정:
    (a) Coordination-only product reframe
    (b) 식당 20곳 timeline 재조정 communication
    (c) P2 segment 별도 acquisition으로 재시도
```

**신뢰도 라벨 (자기 평가):**
- 장소 확정 40% threshold: 중 (한국 모임 문화 가정 의존)
- Click-through 25% threshold: 중하 (산업 benchmark × intent boost factor 곱셈)
- < 10% / < 20% pivot threshold: 낮음 (Phase 2 결과 보고 재설정)

### §9.3. 식당 Retention 패키지 (PRD §13.1 / §16-10 update)

**Incentive:**
- 사인비 ₩0 (기존)
- 활성화 D-day 명시: "Phase 2 검증 후 8주 이내"
- 활성화 후 첫 3개월 수수료 0% (베타 1500원 → 0원)
- 활성화 시 베타 우선 노출 (지도 상단 / 카테고리 첫 결과)

**Communication cadence:**
- 월 1회 progress update (12주 × 1회 = 3-4회)
- 활성화 D-day 2주 전 final notice
- 운영팀 카톡 채널 1:1 SLA 48h (PRD §17.2)

**Fail mode (Pre-mortem):**
- Gate #2 < 10% 시나리오에 대한 식당 communication script 미리 작성
- 3-path 결정 시 식당 영향 분석 + 시점별 대응

### §9.4. Phase 3 (조건부, Gate 통과 시)

순서 (8-12주 추정):
1. 토스페이먼츠 가맹 심사 (1-2주)
2. 통신판매업 신고 (5-7영업일, 관할 구청)
3. 변호사 약관 검토 (1-2주)
4. 사업자 계좌 + 정산용 인프라
5. 식당 활성화 (20곳 사인 → 첫 결제 trigger 활성)
6. 실제 예약·결제·정산·환불·노쇼 flow 활성
7. 푸시 F6·F7 (예약) 활성

## §14. The Assignment (다음 한 주)

**Phase 1+2 모바일 빌드 시작 전, 1주 안에 끝낼 3가지:**

1. **카톡 봇 1주 prototype (cold read 제안 변형)** — Solapi 알림톡 + Next.js + Supabase로 시간 그리드 카톡 link 페이지 만들기. 정의진 + N=4-9명에게 다음 모임 시나리오 재현 시도. **Coordination-only가 standalone 가치 있는지 모바일 출시 전 직접 검증.** (cold read의 falsifiable prediction을 모바일 4-6주 burn 전에 1주에 확인.)

2. **Baseline 측정 design** — 모바일 앱 빌드 시작 전 metric 정의: DAU, 모임 생성률, 시간 확정률, 장소 확정률, click 비율, segment label (P1 학생 / P2 직장인). Phase 1+2 launch 후 2주 baseline 수집할 데이터 schema.

3. **Pre-mortem communication script** — Gate #2 < 10% 시나리오에 대한 식당 20곳 communication script 한 줄이라도 작성. 3-path 결정 (coordination-only / timeline 재조정 / P2 retry) 각각에 대한 식당 message 초안.

이 셋이 Phase 1+2 모바일 출시 burn 들어가기 전 최소 verification + risk hedging.

## §15. What I noticed about how you think

- **"BM을 위해서 C가 필요해."** — D9 답의 한 줄. founder의 strategic framing을 정확히 노출. 분석가가 "Garry red flag"라 짚었을 때 반박 안 하고 다음 정보 (prior MVP + 20곳)를 던져 framing을 재정당화. 한 번에 한 layer씩 명확히 함.

- **"이미 제휴된 식당은... 안암 기준으로 약 20개의 매장과 이전에 만들었던 MVP로 제휴가 되어있어."** — D7 답. 분석가의 "evidence 0" 진단을 한 줄로 무력화. PRD §18을 첫 응답에 sharp하게 명시했으면 이 발견이 더 일찍 나왔을 것 — 그건 향후 communication 디자인 힌트.

- **β-compact 자체 modification.** — 분석가가 β를 권했을 때 100% align 안 하고 자체적으로 Phase 1+2 묶음 + fresh codebase·backend로 변형. trade-off 자체를 명시 (P5 검증 prior MVP signal 자기 평가 의존, fresh-0 acquisition risk, Phase 1+2 진단 분리 어려움). 분석가 의견을 input으로 흡수하되 own design 결정 내림.

- **Gate decomposition + 메타-신뢰도 라벨.** — 분석가가 안 짠 framework까지 회신 (산업 benchmark × intent boost factor, 신뢰도 medium / medium-low / low, "첫 2주 baseline 후 calibrate"). Single threshold → decomposed gate → data-dependent calibration = 3-step elevation.

- **Pre-mortem 명시.** — Cold read interpretation layer를 받아들이면서 "launch 전 fail mode 어떻게 할지 미리 결정 + 식당 communication script 준비"를 own initiative로 추가. YC partner standard practice를 prompt 없이.
